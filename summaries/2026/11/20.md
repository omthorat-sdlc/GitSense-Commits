## 22:06:51
The provided documentation outlines an implementation plan for a "Correction Flow" feature within the Staffolder platform. The core objective is to allow authorized users to amend submitted or signed forms while maintaining strict audit trails and versioning, leveraging existing architectural patterns rather than creating parallel systems.

### Key Implementation Details
*   **Workflow Integration:** The system will introduce a `CORRECTION_REQUESTED` state. Corrections must not overwrite existing records; instead, they will utilize the existing revision architecture to preserve original submissions, signed versions, and historical audit trails.
*   **Role-Based Access Control (RBAC):** 
    *   **Registered Managers (RM):** Granted wildcard authority to correct forms at any lifecycle stage without a mandatory reason.
    *   **Authorized Roles:** Permitted to correct forms based on existing role rules, with mandatory documentation of correction reasons.
*   **Applicant Approval:** A new configuration flag, `requiresApplicantApprovalForCorrection`, will be added to form templates. This ensures that only relevant changes (e.g., declarations or consent) trigger a requirement for applicant review, preventing unnecessary approval cycles for minor administrative fixes.
*   **Data Model & Auditing:** The submission model will be extended to track correction status, assignees, and instructions. Audit logs will be append-only, capturing the actor, timestamp, and diff summaries using existing `forms.diff.ts` functionality.
*   **Frontend UI:** Updates include adding "Send for Correction" actions, specific correction editors, applicant approval views to inspect diffs, and an admin section to toggle approval settings for various system and custom forms.

### Design Principles
*   **Avoid Redundancy:** The plan explicitly mandates reusing existing diff logic, audit infrastructure, and RBAC matrix to ensure consistency.
*   **Security:** Normal form-editing (which is restricted to draft states) will remain untouched. A separate, secure path for correction-edits will be implemented to prevent weakening form security.
*   **Historical Integrity:** The system emphasizes that "a submitted or signed version must never be silently overwritten." All corrections result in new versions linked to their predecessors.
