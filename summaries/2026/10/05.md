**Patterns and Recurring Elements:**

*   **Wizard-Based Form Structure:** Almost all forms are designed as multi-step wizards, using `display: 'step'` for `section` fields in the schema, reflecting a consistent user experience for complex data entry.
*   **Modular Care Plans:** The "Adult Care Plan" is modularized into distinct sections (e.g., Social Support, Nutrition, Mobility, End-of-Life), each represented by its own form schema (`client-XX-acp-*.js`). This allows for flexible and targeted assessments.
*   **Figma-Driven Development:** Comments frequently reference "Figma packs" and "Figma wizard frames," indicating a strong reliance on external design mockups as the source of truth for form structure and visual presentation.
*   **Consistent Styling:** `fieldStyle: 'boxed'` is consistently applied across forms. Various `display` properties like `pills`, `optionCard`, `noteList`, `clauseCard`, `checklist`, `policyGrid`, `dangerNote`, and `infoNote` are used to achieve specific visual and semantic presentations for form elements.
*   **Workflow Integration for Signatures/Reviews:** There's a clear architectural pattern of moving manager signatures and review steps *out* of the form schema and into the overall workflow logic. This separates data capture from approval processes and allows for more flexible role-based permissions at the workflow level.
*   **Data Consistency and Integration:**
    *   Forms frequently leverage "prefilling from carer records" and explicitly link to other forms (e.g., uniform issue and return forms share data).
    *   The `FormRenderer.tsx` introduces `AssessmentLinkContext` to facilitate dynamic linking and data pulling between forms, indicating a robust system for interconnected records.
    *   `optionsSource: 'managers'` is a recurring pattern for dropdowns requiring live lists of personnel, ensuring data accuracy.
*   **Idempotent Seeding:** All form seed data files include `templateId` and `versionId` to ensure that re-seeding operations do not create duplicate or inconsistent records.
*   **Helper Functions for Form Definition:** Common utility functions (`step`, `sub`, `opts`, `buttons`, `q`, `qPair`, `note`) are consistently used in form seed data files, promoting a standardized and readable way to define form elements.
*   **Iterative Refinement:** Multiple identical timestamps for the same file, or small, incremental changes across sequential timestamps, indicate an active and iterative development process for fine-tuning form definitions and frontend rendering logic.
